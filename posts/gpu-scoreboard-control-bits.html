传统 Scoreboard 与现代 GPU 的编译器协同依赖管理

计算机体系结构
Published

September 28, 2026

1. 目标

上一篇文章允许不同执行单元重叠以后，观察到下面的问题：

目标执行单元空闲
不代表指令现在执行是正确的

本文从这个问题开始，先构造传统硬件 scoreboard，再解释论文 Dissecting and Modeling the Architecture of Modern GPU Cores 描述的编译器协同机制。

论文认为现代 NVIDIA GPU 不使用传统的 per-register scoreboard 管理数据依赖。传统 scoreboard 是本文用于比较的中间设计。

2. 固定程序和依赖

继续使用上一篇文章的三条指令：

I1: LOAD R1, [R2]      // 可变延迟，写 R1
I2: ADD  R4, R5, R6    // 与 I1 无关
I3: ADD  R7, R1, R8    // 读取 I1 产生的 R1

此时已经知道 I3 必须等待 I1 产生 R1：

I2 不依赖 I1，可以在 I1 尚未完成时执行。

3. 依赖状态需要对应真实硬件事件

一条指令从发射到结果可见，至少涉及三个不同事件：

issue          指令离开发射位置
register read  指令真正读取源寄存器
write-back     指令结果写回目的寄存器

对于 I1 和 I3 的 RAW：

I1 issue
→ I1 执行
→ I1 write-back R1
→ I3 才能读取 R1

因此，依赖状态不能在 I1 issue 后立即清除。它必须保持到 I1 write-back。

WAR 的解除时刻不同：老指令真正完成 register read 后，年轻 writer 就可以覆盖这个寄存器，不必等老指令 write-back。

这些事件决定了 scoreboard 状态在什么时候设置和清除。

4. 传统硬件 Scoreboard 的内部状态

4.1 指令提供的信息

普通机器指令已经编码：

source registers
destination register
target execution unit

硬件可以用这些寄存器编号查询 scoreboard。

4.2 Writer Scoreboard

为每个可写寄存器保存一个 writer bit：

writer[R] = 1
表示存在一条已经 issue、但尚未 write-back 的指令将写 R

I1 issue 时：

writer[R1] = 1

I1 write-back 时：

writer[R1] = 0

I3 发射前检查所有 source：

writer[R1] == 0
writer[R8] == 0

年轻 writer 还要检查自己的 destination，避免 WAW：

writer[destination] == 0

同一个 writer scoreboard 可以处理 RAW 和 WAW。

4.3 发射机制

候选指令读取：

所有 source 的 writer bits
destination 的 writer bit
目标执行单元状态

只有这些状态都可用，指令才能发射。

在 C2，I3 的橙框包含 R1、R8、R7 和 ALU。R1 仍为黄色使用中，因此 I3 stall。

I1 在 C4 write-back 后，R1 恢复可用，I3 才能发射。

4.4 Reader Scoreboard

writer bit 不能处理 WAR。

如果老指令已经 issue 但尚未完成 register read，年轻指令不能覆盖它的 source register。

因此还需要为每个寄存器记录未完成 reader 的数量：

readers[R]

老指令 issue 时增加 reader count：

readers[source] += 1

真正完成 register read 时减少：

readers[source] -= 1

年轻 writer 发射前检查：

readers[destination] == 0

传统实现因此需要两类状态：

状态 处理的 hazard 清除时刻
writer bit RAW、WAW write-back
reader count WAR register read

5. 现代 GPU 的编译器协同依赖管理

5.1 分工变化

传统 scoreboard 由硬件根据 src/dst 动态恢复依赖。

编译器在生成机器指令时已经知道 I1→I3 的依赖关系。论文描述的机制把这部分信息编码进每条机器指令的 control bits。

编译器负责说明：

producer 更新哪个 Dependence counter
consumer 等待哪个 Dependence counter

硬件负责记录 counter 在运行时是否仍然非零。

5.2 编译后的程序

下面使用简化记号表示 control bits：

#                            S    WB    RD    WAIT
I1: LOAD R1, [R2]         ; 0    SB0   -     {}
I2: ADD  R4, R5, R6       ; 0    -     -     {}
I3: ADD  R7, R1, R8       ; 0    -     -     {SB0}

字段含义为：

字段 含义
S issue 后设置的 Stall counter
WB issue 后递增、write-back 后递减的 counter
RD issue 后递增、register read 后递减的 counter
WAIT 当前指令 issue 前必须为 0 的 counters

I1 的 WB=SB0 表示 I1 issue 后增加 SB0，并在 write-back 时减少 SB0。

I3 的 WAIT={SB0} 表示 SB0 非零时 I3 不能发射。

5.3 硬件状态和发射机制

每个 warp 保存：

一个 Stall counter
六个 Dependence counters：SB0-SB5

当前指令检查：

Stall counter
WAIT mask 指定的 Dependence counters
目标执行单元

I1 issue 后，SB0 在下一周期增加为 1。

I2 的 WAIT 为空，因此可以与 I1 重叠。

I3 检查 SB0。I1 write-back 前 SB0 非零，因此 I3 stall。I1 write-back 后 SB0 归零，I3 才能发射。

5.4 固定延迟：Stall Counter

固定延迟 producer 不需要等待运行时 completion event。

编译器知道 producer latency，可以在 producer 中编码 Stall value：

Stall value
    = producer latency
      - producer 与第一个 consumer 之间的指令数

warp 的 Stall counter 非零时不能继续 issue。计数器每周期减 1，直到归零。

论文通过手工设置过小的 Stall value 得到了错误结果。这说明硬件不会再次根据寄存器编号检查 RAW。

5.5 可变延迟：Dependence Counters

LOAD 和 special-function 指令的延迟不能在编译时确定，因此使用 SB0-SB5。

每条指令可以指定两个要增加的 counter：

  • write-back counter：在 write-back 时减少，用于 RAW/WAW；
  • register-read counter：在 register read 时减少，用于 WAR。

每条指令还包含一个 6-bit WAIT mask，指定 issue 前必须等待哪些 counters 归零。

同一个 counter 可以由多个 producer 增加。consumer 等待 counter 归零，相当于等待这些 producer 全部完成。

5.6 Counter 更新窗口

Dependence counter 在 producer issue 的下一周期才完成增加。

如果 consumer 紧跟 producer，consumer 可能在 counter 增加可见以前进行检查。

这种情况下，producer 还需要设置短的 Stall value，防止 consumer 在下一周期过早发射。

5.7 DEPBAR.LE

DEPBAR.LE 可以等待某个 counter 小于等于阈值，并同时等待一组 counters 归零：

DEPBAR.LE SBx, threshold, {other counters}

它用于多个 producer 共享 counter、但 consumer 只需要等待其中一部分完成的情况。

6. Warp Ready 与 Issue Scheduler

每个 warp 按程序顺序提供最老的指令。

一个 warp 成为 issue candidate，需要满足：

Instruction Buffer 中存在有效指令
Stall counter 为 0
WAIT mask 指定的 counters 满足条件
执行资源可用

论文推断每个 sub-core 每周期最多 issue 一条指令，并使用 Compiler Guided Greedy Then Youngest：

当前 warp 仍然 ready
→ 继续选择当前 warp

当前 warp 不再 ready
→ 选择最年轻的 ready warp

编译器还可以设置 Yield，要求下一周期不要继续选择同一个 warp。

7. 与传统 Scoreboard 的状态量对比

论文建模的传统 scoreboard 需要覆盖每个 warp 的 332 个可写寄存器。

如果 WAR scoreboard 最多支持 63 个 pending consumer，单个 warp 需要：

332 + 332 × 6 = 2324 bit

control-bits 机制需要：

6 × 6 bit Dependence counters
1 × 4 bit Stall counter
1 × 1 bit Yield
= 41 bit per warp

论文估算的面积开销为：

机制 相对 regular register file 的面积开销
传统 scoreboard 5.32%
control-bits 机制 0.09%

传统 scoreboard 支持 63 个 consumer 时，论文测得的平均性能约为 control-bits 机制的 0.98 倍。

8. 总结

传统 scoreboard 的分工是：

机器指令提供 src/dst
硬件根据寄存器编号恢复依赖
硬件按 register read / write-back 更新状态

论文描述的编译器协同机制是：

编译器把依赖编码成 S、WB、RD、WAIT
硬件维护 Stall counter 和 SB0-SB5
counter 状态与执行资源共同决定 warp 是否 ready
scheduler 从 ready warps 中选择一条指令
