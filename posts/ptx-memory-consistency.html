从数据交接理解 GPU 内存一致性

体系结构
从一个生产者与两个消费者的缓冲区交接开始，逐步理解内存顺序与同步。
Published

October 29, 2026

上一篇关于指令发射与依赖管理的文章讨论一条指令什么时候可以发射。本文从一个数据交接程序开始，回答三个问题：程序员期望读到什么值；系统的优化为什么会改变结果；程序怎样写出它需要的保证。

全文使用同一个主例子。每一步只改变一个条件，然后说明出现的问题和需要补上的保证。

1 理想的执行

1.1 三个线程交接一个缓冲区

生产者 P 把一份数据写进缓冲区，消费者 C1、C2 读这份数据。两个消费者都读完以后，P 才能覆盖缓冲区，写入下一份数据。

下面用 Python 的写法表示三个线程的程序。三个线程共享 data、full、done1、done2、empty，初值都是 0。

生产者 P 消费者 C1 消费者 C2 
data = 42
full = 1
while empty != 1:
    pass
data = 43
 
while full != 1:
    pass
value1 = data
done1 = 1
if done2 == 1:
    empty = 1
 
while full != 1:
    pass
value2 = data
done2 = 1
if done1 == 1:
    empty = 1

P 写好数据以后，把 full 设为 1，通知两个消费者。每个消费者读完数据以后，把自己的 done 设为 1，再检查对方的 done。发现两个都已读完的消费者，把 empty 设为 1，通知 P 可以复用缓冲区。代码中的 while ...: pass 表示一直检查，直到条件成立。

期望的结果是：两个消费者都读到 42，P 收到通知，然后写入下一份数据 43。本文只看这一轮交接。

1.2 理想的交接与读值规则

先假设各线程按程序顺序交错执行，每一步完成一次访问。时间线中的 t1–t13 只表示先后，省略了等待时的重复检查。

程序顺序（program order）是同一个线程内访问的先后，也就是代码中的顺序。它只规定代码的先后，不规定访问在硬件上什么时候发出、什么时候完成。

在单线程中，一次读读到程序顺序中同一位置最近一次写的值。多个线程共享存储时，不同线程的读写之间没有这种先后，所以要用规则来确定读到的值。

内存一致性模型规定共享存储系统对程序员表现出的行为，也就是读操作可以返回哪些值。它是程序员与系统之间的接口。1

本例对 data 有三次写：初始写入 0、P 写入 42、P 写入 43。模型规定 C1 读 data 时，可以读到其中哪些写的值。

这次执行把所有访问交错成一条序列，这条序列保留各线程的程序顺序。每次读都读到序列中同一位置在它之前最近一次写的值。这符合顺序一致性的要求：

顺序一致性（Sequential Consistency，SC）要求：每次执行的结果，都能用一条全局访问序列解释。这条序列保留各线程的程序顺序，并且每次读都读到同一位置在它之前最近一次写的值。2

SC 只约束能观察到的结果，硬件内部仍然可以并行。用 SC 分析本例：C1 读到 full == 1 时，全局序列中一定有下面的先后：

P 写 data=42 → P 写 full=1 → C1 读 full==1 → C1 读 data

两端的先后来自各自的程序顺序。中间的先后来自一个事实：C1 读到了 P 唯一一次写入的 full = 1。所以 C1 读 data 排在 P 写 42 之后，不能读到初值 0。

2 fence：把顺序补回来

第 1 节假设每次访问一步完成。真实的机器把一次访问分成两步：发出和完成。写的完成叫生效，生效以后别的线程才能读到它写的值；读的完成是读到值。两步之间可以隔一段时间，所以后面的访问可能先完成，同一个线程中两次访问的先后不再可靠。

下面的时间线中，● 表示发出，◆ 表示完成。

2.1 写缓冲与读旁路

写发出以后，值不一定马上进入存储。硬件给每个线程一个私有的队列。写先进入队列，线程不等它生效就继续执行，所以写生效的时间推后了。在这段时间里，后面读别的地址的读可以越过这个写，直接从存储读到值。

写缓冲就是这个队列，它位于写发出之后、进入共享存储系统之前。写在队列中时，别的线程看不到它；写离开队列时才生效。同一个队列中的写先进先出，所以写与写之间的顺序不变。3

在本例中，C1、C2 各自先写自己的 done，再读对方的 done。

下面的图把代码和时间线放在一起。先点运行，看不打开优化时的结果；再打开写缓冲，运行一次，对比结果。

打开写缓冲以后，两个读在 t3、t4 完成，两个写在 t5、t6 才生效。读完成时写还在缓冲中，所以两个读都读到 0。没有消费者写 empty，P 一直收不到通知。

在写和读之间插入一行 fence.sc.gpu 以后，写先生效，读才发出，顺序恢复了。

程序中写在前、读在后，图中却是读先完成：完成的顺序与程序顺序不一致。把写记作 W、读记作 R，这一对就是 W→R。模型允许这种不一致，叫作 W→R 被松弛。

TSO（Total Store Order）：每个线程有一个先进先出的写缓冲。写进入缓冲就算提交；读可以越过还没生效的写；写与写之间保持顺序。

只松弛 W→R 的模型有三个：IBM 370、TSO、PC。x86 属于 TSO。

2.2 写操作重叠

存储分成多个模块。一个模块忙时，另一个模块还能接收新的写。所以同一个线程的多个写可以同时在途，各自生效的时间互不相关，后发出的写可能先生效。

写操作重叠指同一个线程的多个写不等前一个生效就发出，生效的先后也不再由发出的先后决定。4

在本例中，P 先写 data（42），再写 full（1）。

下面的图把代码和时间线放在一起。先点运行，看不打开优化时的结果；再打开写重叠，运行一次，对比结果。

打开写重叠以后，两个写生效的先后反了：full 在 t3 生效，data 在 t6 才生效。C1 仍然按顺序读，在 t4 读到 full == 1。但这时 data 还没有生效，所以 C1 读到 0。

在两个写之间插入一行 fence.sc.gpu 以后，data 先生效，full 才发出，顺序恢复了。

程序中 data 在前、full 在后，图中却是 full 先生效：完成的顺序与程序顺序又不一致。这一对是写和写，记作 W→W。模型允许这种不一致，叫作 W→W 被松弛。

PSO（Partial Store Order）：在 TSO 的基础上再松弛 W→W，写与写之间的先后也不保证，要用 STBAR 恢复。

只松弛 W→R 和 W→W 的模型是 PSO，SPARC 的 PSO 属于这一类。写的一侧保序以后，读的一侧还可能出问题。

2.3 非阻塞读

读要等存储把值送回来。在这段时间里，处理器不空等：它让这个读继续等待，同时执行后面的指令，包括后面的读。所以后面的读可能先读到值。

非阻塞读指一次读发出以后，不等值返回，后面的读就可以发出，并且可能先读到值。两次读完成的顺序可以反过来。5

在本例中，C1 先等到 full == 1，再读 data。

下面的图把代码和时间线放在一起。先点运行，看不打开优化时的结果；再打开非阻塞读，运行一次，对比结果。

打开非阻塞读以后，读 data 在 t1 发出，比读 full 早。full 变成 1 时，读 data 带回的值仍然是 0。

在两次读之间插入一行 fence.sc.gpu 以后，第二次读要等第一次读完成才发出，顺序恢复了。

程序中先读 full、后读 data，图中却是读 data 先发出：访问的顺序与程序顺序又不一致。这一对是读和读，记作 R→R。模型允许这种不一致，叫作 R→R 被松弛。

松弛全部程序顺序的模型有六个：WO、RCsc、RCpc、Alpha、RMO、PowerPC。这些模型连 R→R 也不保证。需要顺序的地方，全部靠显式的 fence 或同步操作。

2.4 读与后续写重叠

读要等存储把值送回来，写却不用等：写发出以后，线程就能继续执行。硬件没有理由让后面的写等这个读：

  • done1 的值是常数 1，与这次读的结果无关。
  • 读可能很慢。后面的写也停下来等，只会浪费时间。
  • 两次访问之间没有依赖，所以写可以排到读前面。

读与后续写重叠指一次读发出以后、值还没返回时，同一个线程后面的写已经生效。6

在本例中，C1 先读完 data，再写 done1 = 1，告诉别的线程我读完了。

下面的图把代码和时间线放在一起。先点运行，看不打开优化时的结果；再打开读与后续写重叠，运行一次，对比结果。

打开以后，读 data 在 t1 发出，done1 在 t2 生效。这个消息经过 C2 传到 P，P 在 t3 写入 43。读 data 在 t5 才返回，读到的是 43。读发出时，这个值还不存在。1.2 的推理链在这里反了过来。

在读和写之间插入一行 fence.sc.gpu 以后，读先读到值，写 done1 才发出，推理链不能再反过来。

程序中先读 data、后写 done1，图中却是 done1 先生效：完成的顺序与程序顺序又不一致。这一对是读和写，记作 R→W。模型允许这种不一致，叫作 R→W 被松弛。

我读完了这个消息还经过另外两处 R→W：C2 读完 done1 以后写 empty；P 读完 empty 以后写 43。在 PTX 中，控制依赖不保证顺序（见 6.3），所以每一处都要加 fence。松弛的顺序越多，要加的 fence 越多。

松弛全部程序顺序的模型有六个：WO、RCsc、RCpc、Alpha、RMO、PowerPC。本节讲的是 Alpha、RMO、PowerPC 这一组，它们用显式的 fence 恢复顺序。另外三个模型 WO、RCsc、RCpc 也松弛全部程序顺序，但它们把访问标成同步操作来恢复顺序。

看这些 fence 的位置，可以发现两件事。第一，fence 从不紧挨 data，只紧挨三个标志（full、done、empty）。第二，fence 的位置只有两种：在写标志之前（交出），或在读到标志之后（拿到）。只有 2.1 的那一处是例外，它在写自己的 done 和读对方的 done 之间。

3 release 与 acquire

第 2 节的方法是在每一处需要顺序的地方插入 fence.sc。按 2.5 的程序，三个线程交接一份数据要用 10 个 fence。而且读代码的人看不出每个 fence 的用意：哪一处是交出，哪一处是拿到。

本节换一套方法。先把访问分成两类，再让交出的写和拿到的读自己带上语义。fence 只留在剩下的少数位置。

3.1 区分内存操作

到这里为止，模型对所有访问一样对待。但在实际程序中，访问的作用不同：full 替 data 排好了先后，full 自己却没有保护，另一个线程随时可能同时写它。WO 模型（Weak Ordering，弱序）先在这里分出一层：7

特殊操作（special）是这样的访问：别的线程可能同时访问同一个位置，并且两个访问中至少有一个是写。其余的访问叫普通操作（ordinary）。要保证两个操作之间的先后，两者中至少要有一个是特殊操作。8

在本例中：

变量 被多个线程访问 可能同时被访问 分类
data 是 否：full 让 P 和 C1 错开 普通操作
full 是 是：C1 反复读时，P 可能正在写 特殊操作
done1、done2 是 是：一个消费者读时，另一个可能正在写 特殊操作
empty 是 是：P 反复读时，消费者可能正在写 特殊操作

共享不等于特殊。多个线程都访问 data，但 data 前后有 full 和 done 隔开，两个线程不会同时访问它。第 2 节的交接保证的正是这一点。分类以后，模型只对特殊操作保证顺序。两个特殊操作之间的普通操作，仍然可以重叠，也可以乱序。

用 2.5 的程序对照：等 full → 读 data、读 data → 写 done1、写 done1 → 读 done2，每一对中至少有一个是特殊操作，所以都保序。如果 C1 连续读 100 次 data，这 100 次读之间没有任何顺序保证。

RC（Release Consistency，释放一致性）模型在这棵树上再分一层。9 特殊操作中，用来交接的叫同步操作（sync），其余的叫非同步操作（nsync）。同步操作又分两种：为了拿到访问权而做的读叫 acquire，为了交出访问权而做的写叫 release。

内存操作
├─ 普通操作（ordinary）                     读 data
└─ 特殊操作（special）
   ├─ 非同步操作（nsync）                   3.5 节介绍
   └─ 同步操作（sync）
      ├─ acquire：为拿到访问权而做的读      等 full、等 empty、读到对方的 done
      └─ release：为交出访问权而做的写      写 full、写 done、写 empty

三种 fence 的差别如下。上面下面指同一个线程中 fence 之前、之后的访问：

fence 要等的上面的访问 要拦住的下面的访问 保序的对
fence.sc 读、写 读、写 四种全部
fence.release 读、写 只拦写 W→W、R→W
fence.acquire 只等读 读、写 R→R、R→W

release 和 acquire 合起来，还缺 W→R 这一对。只有 fence.sc 能保证这一对的顺序，见 3.6。

3.2 release：交出之前先完成

2.5 的程序中，P 交出 data 时用的是 fence.sc。但 P 在这里只需要一件事：data 生效以后，full 才生效。

在本例中，把 P 的 fence.sc 换成 fence.release，C1 不变。

下面的图打开第 2 节的全部优化。先用 fence.sc 运行一次，再换成 fence.release 运行一次，对比结果。

  • data = 42 → 读 empty 没有亮。提前读 empty 没有害处：如果读到 0，P 只要再等一轮。

3.3 acquire：拿到之后再进行

2.5 的程序中，C1 拿到 data 时用的也是 fence.sc。但 C1 在这里只需要一件事：读到 full == 1 以后，才读 data。

在本例中，P 用 3.2 的 fence.release，C1 先不加 fence。

下面的图打开第 2 节的全部优化。先不给 C1 加 fence，运行一次；再加上 fence.sc；最后换成 fence.acquire。对比三次的结果。

C1 不加 fence 时，r1 是 0：读 data 在 t1 就发出了。P 的 release 只对 P 自己的两个写保序，对 C1 没有作用。加上 fence.sc 或 fence.acquire 以后，r1 都是 42，两条时间线完全相同。

把 C1 的代码按 fence 分成上下两部分，再按读写分开，画成四象限图。acquire 点亮从上·读出发的箭头：

  • while full != 1 → r1 = data 亮了。拿到就靠这一条。
  • 上·写是空的：C1 在 fence 上面没有写。fence.sc 比 fence.acquire 多等的只有这一格，所以这里两者效果相同。

3.4 release 与 acquire 配合

两种操作合起来，正好补上 2.2、2.3、2.4 的问题。2.1 的问题留到 3.6。按这个方法改写 2.5 的程序：

    pass
fence.acquire.gpu
data = 43
 
while full != 1:
    pass
fence.acquire.gpu

fence.release.gpu
done1 = 1
fence.sc.gpu
if done2 == 1:
    fence.acq_rel.gpu
    empty = 1
 
while full != 1:
    pass
fence.acquire.gpu
value2 = data
fence.release.gpu
done2 = 1
fence.sc.gpu

    fence.acq_rel.gpu
    empty = 1

fence 仍然是 10 个，但只剩两个 fence.sc（2.1 那一处 W→R）。其余的都换成了开销更小的 fence.release 或 fence.acquire，而且 fence 的名字直接说明了用意。

fence.sc 比 release、acquire 多保证一对 W→R 的顺序。为此，下面的读要等上面的写离开写缓冲（2.1），才能读到值。写常常很慢，读也只能一起等，所以 fence.sc 的开销最大。10

写 empty 之前用的是 fence.acq_rel：读到对方的 done 是拿到，写 empty 是交出，这个 fence 两种作用都有。11

下面把整个程序运行一次，只看一件事：C2 读完 data 以后，P 怎样知道这件事。P 与 C2 从不直接通信，这个消息要经过 C1 接力。

在 C2 读 data 和 P 写 43 之间，有五条边：

  1. C2 的 release 使读 data 排在写 done2 之前。
  2. C1 读到 done2。
  3. C1 的 fence.acq_rel 使读 done2 排在写 empty 之前。
  4. P 读到 empty。
  5. P 的 acquire 使读 empty 排在写 43 之前。

第 2、4 条边把两个线程连起来：一端是 release 写，另一端是 acquire 读，并且这个读读到了这个写的值。本文把这种连接叫作接上。五条边连成一条链，所以 C2 读 data 排在 P 写 43 之前，C2 读不到 43。

去掉 C2 的 fence.release 以后，第一条边断开：读 data 还没返回，done2 已经生效。后面四条边照常连上，所以 P 写入 43 时，C2 还没读完 data。

PTX 把由程序顺序和读到连成的先后叫作因果序（causality order）。它的作用相当于 C++ 的 happens-before。

3.4 的程序中还有两个 fence.sc 没有说明。它们决定 C1、C2 中谁最后完成：两个消费者各写自己的 done，再读对方的 done。至少要有一个消费者读到 1，由它写 empty。

换成 fence.sc 以后，两个读中一定有一个读到 1。所有 fence.sc 排成一个先后，两个 fence.sc 中总有一个在前。17 在前的 fence.sc 相当于 release，在后的相当于 acquire，两者不用读到值就能接上。图中 C1 的 fence.sc 在前，紫色箭头就是这条边：C1 写 done1 排在 C2 读 done1 之前，所以 C2 读到 1，由 C2 写 empty。如果 C2 的 fence.sc 在前，结果相反，C1 读到 1。18

4 atom

3.6 用 fence.sc 决定 C1、C2 中谁最后完成，但 fence.sc 的开销最大（3.4）。另外，消费者越多，每个消费者要读的 done 越多。

另一种方法是用一个计数 count 代替两个 done。每个消费者把 count 加 1，读到旧值 1 的消费者是最后一个，由它写 empty。每个消费者只访问 count 这一个位置，不再有写自己的、读对方的这一对 W→R，所以不需要 fence.sc。

本节先保证计数正确，再逐步改进这个方法，最后得到 barrier：P 直接等完成的人数。

4.1 atom：读改写一步完成

先用第 3 节的方法：读出 count，写回加 1 的值，前后的 fence 按 3.4 放好。下面按 1.2 的理想执行运行一次，不打开任何优化：

C2 的读插在 C1 的读和写之间：两个消费者都读到 0，count 只加到 1，没有消费者写 empty。

fence 在这里没有作用。fence 只管一个线程内部的先后，而每个线程自己的读和写都没有乱序。问题是别的线程的写插在了中间。这里需要另一种保证：读、加 1、写回作为一步完成，别的线程的写不能插在中间。这种保证叫不可分割。fence 不能提供不可分割，PTX 用 atom 指令提供它。

把读和写换成一条 atom.add，fence 不变，结果就正确了：先加的消费者读到 0，后加的消费者一定读到 1，由它写 empty。19

atom 中的原子指不可分割，与第 3 节的顺序是两件事。atom.add 不写 .sem 时是 relaxed：它只保证不可分割，不带顺序，所以前后的 fence 都要保留。20

4.2 .scope：原子性也有范围

C1、C2 在不同的 CTA 中。现在 C1 的 atom 写成 .cta（例如，从只在一个 CTA 中运行的代码复制过来），C2 写成 .gpu。

atom.cta 只保证本 CTA 的线程不能插在中间，C2 不在本 CTA 中。从 C2 看，C1 的读改写被分成了两步，C2 的读改写插在中间，两个消费者又都读到 0。21 每个读改写本身仍然是一步完成的，只是完成的位置不同：可以认为 atom.cta 在本 SM 这一层完成，atom.gpu 在 L2 完成，两者都不能阻止对方。22

规则与 3.5 的 scope 规则相同：两端的 scope 都要包含对方。在 3.5 中，这条规则决定读到的值是否构成通信；在这里，它还决定不可分割是否成立。修复方法是两端都写 .gpu。scope 要包含所有可能同时修改这个位置的线程。

3.5 说明过，st、ld 可以直接带 release、acquire，不再需要旁边的 fence。atom 也一样：.sem 可以写 .release、.acquire、.acq_rel。下面改写 4.1 中 C1 的代码：

两个 fence 分别移到它们服务的访问上：

  • fence.release 在 atom 前面，只为这个 atom 做 release。移进 atom 以后，atom 带上 release 这一半。
  • fence.acq_rel 在 atom 和写 empty 之间，同时为两个访问服务。它的 acquire 一半给前面的 atom：读到 1 时，拿到对方交出的结果。它的 release 一半给后面的写 empty：把结果交给 P。分开以后，atom 再带上 acquire 这一半，写 empty 标成 st.release。

4.4 barrier：P 直接等人数

4.3 的交接多了一步：最后一个消费者先用 acquire 拿到对方交出的结果，再写 empty 交给 P。所以两个消费者都要带 acquire，还要多写一个 empty。

现在改成 P 直接等 count 变成 2，再写 43。P 等的是已经完成的人数，这就是 barrier。5.2 的 mbarrier 也是这样计数。消费者不用再判断谁是最后一个，只要交出：两个消费者都写 atom.release.add，不用 acquire，也不写 empty。P 用 ld.acquire 读 count。

P 读到的 2 是后加的消费者写的，所以 P 与它直接接上。先加的消费者只写了 1，P 从来没有读到这个 1。下面说明：先加的消费者交出的 data，P 也拿到了。

2 是在 1 的基础上加出来的。读改写会把读到传下去：P 读到 2，就算读到了 1。25 图中从先加的消费者直接连到 P 的橙色箭头就是这条边。

所以 P 等到 2，就等于等到了两个消费者。点C2 先加，两个消费者的先后互换，P 的代码和结果都不变。P 需要的是两个消费者都排在它之前，不需要知道 C1、C2 谁先。

5 异步拷贝与 proxy

前四节中，data 一直由 P 用普通的 st 写入。实际的 kernel 很少这样搬运数据。kernel 通常用异步拷贝把一块 tile 从 global memory 搬到 shared memory，P 只负责发出拷贝。

本节换一个场景，名字不变：P、C 是同一个 CTA 中的两个 warp，data 在 shared memory 中。P 把一块 tile 搬进 data，然后通知 full；C 等到 full 以后读 data，读完以后通知 empty。

5.1 cp.async：拷贝不在程序顺序里

P 用 cp.async 把 tile 从 global memory 直接搬进 data，不经过寄存器。full 用一个 named barrier：P 执行 bar.arrive 通知，C 执行 bar.sync 等待。30

C 读到的是旧值。cp.async 发出以后，拷贝单独进行，P 不等拷贝完成就执行 bar.arrive。这是本文第一次出现不在程序顺序中的操作：这个拷贝虽然写在 bar.arrive 前面，但它不算 P之前的访问，所以 bar 不对它保序。31

修复方法是先等拷贝完成：cp.async.wait_all 使 P 停下来，等它发出的拷贝全部完成，再执行 bar.arrive。32

执行 wait 以后，仍然要保留 bar：wait 只使拷贝的结果对 P 自己可见。要把结果交给 C，还要同步一次。33

这里的 bar 是第三种同步。它与 3.6 的 fence.sc 一样，不用读到值：bar.arrive 与同一个 barrier 上的 bar.sync 直接接上，就是图中的紫色虚线。它的范围固定是本 CTA。34 到这里，三种同步都出现了：release 和 acquire 要读到值才接上（第 3 节），fence.sc 和 barrier 不用读到值。

5.3 proxy：两条访问路径

data 要复用：C 读完第一块，用 mbarrier.arrive 通知 empty；P 等到 empty 以后，用 TMA 把第二块写进同一个 data。按第 3 节的规则，先后已经排好。C 的读在 arrive（release）之前，P 的 try_wait（acquire）在发出 TMA 之前。37

6.2 morally strong 与数据竞争

两个操作 morally strong（§8.7），要同时满足三条：50

  1. 在同一个线程里；或者两端都是 strong，并且各自的 scope 包含对方的线程（3.5、4.2、5.4）。
  2. 使用同一个 proxy（5.3）。
  3. 如果都是内存访问，访问的字节完全重叠。

PTX 的大部分公理只对 morally strong 的操作成立。

冲突与数据竞争（§8.7.1）：

  • 冲突：两个重叠的内存操作，至少一个是写。
  • 数据竞争：冲突的两个操作，既没有被因果序（6.3）排出先后，又不是 morally strong。
冲突的一对 ─┬─ 因果序排出了先后 ──► 不是数据竞争
            ├─ morally strong ────► 不是数据竞争
            └─ 两样都没有 ────────► 数据竞争

数据竞争的后果（§8.7.2）分两种：

  • 两个操作的字节完全重叠（uniform-size）：公理仍然适用，读可能读到任何一个没有被公理排除的写的值。
  • 两个操作只部分重叠（mixed-size）：程序中只要有一处，全部公理都不适用。

这一点与 C++ 不同：在 C++ 中，有数据竞争的程序，整个行为都未定义。51

6.3 关系：前文箭头的正式名称

先是两种 pattern（§8.8）：

  • release pattern（在位置 M 上）有两种写法：M 上的一个 release 操作；一个 release fence 后面接 M 上的 strong 写。它只影响 pattern 第一条指令之前的操作。
  • acquire pattern（在位置 M 上）有两种写法：M 上的一个 acquire 操作；M 上的 strong 读后面接一个 acquire fence。它只影响 pattern 最后一条指令之后的操作。
  • red 里的读不构成 acquire pattern（4.5）。52

然后是 §8.9 的几种关系：

  • release pattern X 与 acquire pattern Y（3.4）：X 中的写在 observation order 中排在 Y 中的读之前。另外，X 的第一个操作和 Y 的最后一个操作要 morally strong。
  • fence.sc X 与 fence.sc Y：X 在 Fence-SC order 中排在 Y 之前（3.6）。
  • bar.arrive、bar.sync 与同一个 barrier 上的 bar.sync（5.1）；barrier.cluster.arrive 与 barrier.cluster.wait（5.4）。

  1. base causality order：程序顺序和 synchronizes 可以任意首尾相接，并且可以传递。这种传递就是同步的累积性：一个线程交出的结果，可以经过中间的线程，传到后面的线程（3.4 的接力）。
  2. proxy-preserved base causality order：上一层的先后，只在下面三种情况下保留（5.3）：
    • 两次访问同一地址，都使用 generic proxy。
    • 两次访问同一地址，使用同一个 proxy，并且在同一个 CTA 中。
    • 两次访问是 alias，并且路径上有 alias proxy fence。
  3. causality order：在上一层的基础上，再加一种不传递的边。如果 W 在 observation order 中排在 Z 之前，并且 Z 在上一层中排在 Y 之前，那么 W 排在 Y 之前。

数据、地址、控制依赖都不在这些关系里，PTX 只在 No Thin Air 公理里提到依赖（2.4）。

6.4 公理：限制读能读到的值

六条公理（§8.10）：

Coherence 因果序中在前的写，coherence order 中也在前 —
Fence-SC Fence-SC order 不与因果序矛盾 3.6

Causality 公理落到读上，是两条排除规则（§8.10.6）：

  • 读 R 在因果序中排在重叠的写 W 之前：R 不能读 W。
  • 写 W 在因果序中排在重叠的读 R 之前：R 不能读 coherence order 中排在 W 之前的写。

每个字节在所有线程开始之前，都有一次初始写（§8.2.6）。

6.5 PTX 在综述中的位置

按综述 Table 1 的几列看 PTX：

综述的列 PTX
松弛 W→R、W→W、R→RW 都松弛（第 2 节）
读到别人的写过早（写原子性） 允许，PTX 不是 multi-copy atomic
安全网 单独的 fence；标在访问上的 .release、.acquire 等；atom；barrier
  • 写原子性有两条要求：同一位置的写，所有线程看到的先后相同；一次写对所有线程都可见之前，任何读都不能读到它的值。对 morally strong 的访问，PTX 保证第一条（coherence order 与 SC per location），不保证第二条。53
  • 同步只有三种：release、acquire 配对；fence.sc；barrier（5.1）。
  • 在同步操作之间，PTX 像 RCpc：release 后面接 acquire 不保序，要 fence.sc 补（3.6）。
  • 综述的模型没有的两根轴：scope 规定与哪些线程，proxy 规定使用哪个通路。

6.6 小结：一次读可以读到哪个值

一次读 R 可以读到哪个写的值
├─ 候选：同一位置的全部写，包括初始写（§8.2.6）
├─ 排除：Causality 公理（6.4）
│  ├─ 因果序：程序顺序 + 同步，可以传递；再加经过 observation order 的边（6.3）
│  │  ├─ 同步：release、acquire 配对；fence.sc；barrier
│  │  └─ 只在同一个通路中保留：proxy
│  └─ observation order 要求两端 morally strong：strong、scope、同一个 proxy（6.2）
├─ 同一位置的保证：Coherence、SC per location、Atomicity
└─ 数据竞争：没有被公理排除的写都可能读到（6.2）
